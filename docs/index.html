Your pure functions, on every CPU core, in the browser and Node.js

parallel map · filter · reduce auto-split TypedArrays loop-unrolled matmul typed module workers batching · streaming · priorities zero dependencies

defuss-multicore wraps a pure function and runs it across all cores: Web Workers in the browser, worker_threads in Node.js — the same import, the same call. Array and TypedArray arguments are auto-split into partitions, scalars broadcast to every worker, and partial results stream back through your reducer. The same package ships JIT loop-unrolled vector and matrix kernels, and typed module workers with task pools: batching, streaming, priorities, timeouts and cancellation.

One API, both runtimes

Web Workers in the browser, worker_threads in Node.js, behind one isomorphic API: the import and the call site never change, and the same tests run in vitest on both sides.

Auto-split and broadcast

Array and TypedArray arguments are partitioned across cores; scalars broadcast to every worker. Below the threshold, the caller thread runs the function directly.

Loop-unrolled kernels

dotProduct, matmul, matadd and friends are JIT-specialized with 4×/8×/16× unroll factors, auto-selected per shape — up to 2.4× over naive loops.

Parallel map · filter · reduce

The trio for any array, distributed across pooled workers that expire when idle. One pool is cached per callback and core count; releaseArrayWorkers() drops it on demand.

Typed module workers

createPool<typeof tasks>() drives real ESM worker modules — imports and module-local state included — with batching, streaming, priorities, timeouts and cancellation.

Zero dependencies

Dual ESM + CJS output with no runtime dependencies. Transferable buffers move partitions zero-copy; your caller-owned buffers stay attached.

How it works

⚡ One wrapper: split, dispatch, stream, merge

multicore(fn) serializes your function with fn.toString() and rehydrates it inside one worker per CPU core. Each call partitions the array arguments, broadcasts the scalars and collects the partial results — with an optional reducer to merge them into a single value. Small inputs never leave the caller thread.

Scroll the diagram sideways to see the whole dispatch.

One wrapper, three ways to consume

fn is serialized via fn.toString() and rehydrated inside every worker, so it must be self-contained: no captured closures, no imports, no DOM access. Everything it needs arrives as arguments; async chunk functions are awaited. Need real imports and module state? Use module workers with a task pool instead.

The call returns a ParallelResult<R> — both PromiseLike<R[]> and AsyncIterable<R>: await it for the collected results, or for-await to stream each worker's partial as it finishes. With a reduce option the partials merge into one value. The callable also exposes warmup(), close() and terminate().

import { multicore } from "defuss-multicore";
 
const parallelSum = multicore(
  (chunk) => chunk.reduce((a, b) => a + b, 0),
  { reduce: (a, b) => a + b },
);
 
const total = await parallelSum(millionsOfNumbers);

Start simple, escalate when needed

Most parallel work is a pure function over a batch: multicore() wraps it, the threshold keeps small inputs on the caller thread, and a reducer merges the partials. The trio covers the cases that read better as map, filter or reduce.

When the worker needs real imports, module-local caches between jobs, or per-job control — priorities, timeouts, streaming in completion order — promote it to a typed worker module driven by a task pool. The math ops stay synchronous by design: dispatch overhead would eat their millisecond-scale wins.

  1. multicore() · map · filter · reduceA pure function over a batch, no state: the simplest form, and the one the threshold guard is built for.
  2. createPool() module workersReal ESM with imports and module-local caches: batching, streaming, priorities, timeouts and cancellation.
  3. dotProduct · matmul · matadd · …Loop-unrolled math on the caller thread: synchronous, no dispatch at all — or call them inside your workers.
import { createPool } from "defuss-multicore";
import type { tasks } from "./worker.js";
 
const pool = createPool<typeof tasks>({
  worker: () => new Worker(new URL("./worker.ts", import.meta.url), { type: "module" }),
  maxWorkers: 4,
});
 
const input = new Float64Array([1, 2, 3]);
const { values } = await pool.run("double", input, { transfer: [input.buffer] });
Examples

🧩 Four entry points, one mental model

Every snippet below is real code from the README and the examples folder — pick the primitive that matches your workload, not the other way round.

Wrap any pure function

multicore() serializes fn into each worker, so the function must be self-contained: no captured closures, no imports, no DOM. Async chunk functions are awaited.

  • Await the call for all partial results — or one value with reduce.
  • for await streams results as workers finish, in submission order.
  • Per call: override cores, pass an AbortSignal, or disable partition transfer.
const parallel = multicore(heavyComputation);
 
for await (const result of parallel(data)) {
  console.log("worker finished:", result);   // stream as each worker finishes
}
 
const controller = new AbortController();
const pending = parallel(data, { signal: controller.signal });
setTimeout(() => controller.abort(), 5000);   // cancel the in-flight workers

The parallel trio

map, filter and reduce distribute any array across the pool and flatten the results. One pool is cached per callback and core configuration; idle workers expire on their own.

  • The reducer must be associative — regrouping changes floating-point rounding.
  • releaseArrayWorkers(callback) drops a cached pool explicitly.
import { map, filter, reduce } from "defuss-multicore";
 
const doubled = await map(hugeArray, (x) => x * 2);
const evens   = await filter(hugeArray, (x) => x % 2 === 0);
const sum     = await reduce(hugeArray, (a, b) => a + b, 0);   // associative

Real modules, typed end to end

Module workers are normal ESM: imports, module-local state, async handlers. expose() awaits init before accepting tasks; createPool<typeof tasks>() gives the caller the task names and payload types.

  • run / batch / stream with chunkSize and concurrency.
  • priority, timeoutMs, signal and explicit transfer lists per job.
  • Keep the new Worker(new URL(...)) expression at the call site so Vite bundles the worker graph.
import { expose, transfer } from "defuss-multicore/worker";
 
let calls = 0;   // module-local state survives between jobs
export const tasks = {
  async counter(_) { return ++calls; },
  double(values) {
    for (let i = 0; i < values.length; i++) values[i] *= 2;
    return transfer({ values }, [values.buffer]);   // explicit zero-copy move
  },
};
await expose(tasks, { init: async () => { calls = 0; } });
import { createPool } from "defuss-multicore";
import type { tasks } from "./worker.js";
 
const pool = createPool<typeof tasks>({
  worker: () => new Worker(new URL("./worker.ts", import.meta.url), { type: "module" }),
});
 
for await (const { index, value } of pool.stream("double", jobs)) {
  console.log(index, value);   // completion order across chunks
}
await pool.close();

Loop-unrolled linear algebra

The math ops run synchronously on the caller thread — JIT-specialized kernels with 4×/8×/16× unroll factors, auto-selected per shape. Call them inside a multicore() function or a task pool to run them off-thread.

  • dotProduct(as, bs): batch dot product of vector pairs → Float32Array.
  • matmul(A, B): transpose-optimized multiplication → Float64Array rows.
  • matadd / matsub / matdiv: element-wise, loop-unrolled.
import { dotProduct, matmul, matadd } from "defuss-multicore";
 
const scores = dotProduct(embeddings, queries);   // 100K pairs × 768-dim → Float32Array
const C      = matmul(A, B);                      // MxK · KxN → MxN, transpose-optimized
const sum    = matadd(A, B);                      // element-wise, on the caller thread

Parallelize these

  • Key derivation / password hashing — thousands of rounds per item (4.89×)
  • Batch checksumming (CRC32, SHA, …) of large messages
  • Heavy per-element work — image processing, physics simulation, compression
  • Any workload where each chunk runs >5 ms on a single core

Leave these on the main thread

  • Simple reductions (sum, min, max) — the main-thread loop beats dispatch
  • Trivial transforms — memory-bandwidth bound, not CPU-bound
  • Small arrays (<1024 elements) — the threshold option exists for this
  • Single function calls — multicore is for batches
  • I/O-bound work — fetch, file reads and DB queries are already async

* One machine, one runtime, no control group; the workloads are illustrative, not controlled benchmarks. Four warmed workers were ~2.55× faster than the caller thread on the pool workload, but cold startup exceeded the task duration and one worker was slower than no workers — persistent reuse and sufficiently large jobs matter.

API

📐 A small surface, typed end to end

Signatures and defaults are verbatim from the README (opens in a new tab); the types ship with the package, dual ESM + CJS.

multicore(fn, options?)

The returned callable is both PromiseLike<R[]> and AsyncIterable<R> — await the collected results or stream them as workers finish — and exposes warmup(), close() and terminate().

MulticoreOptions<R>
Option Type Default Description
coresnumberavailable CPU coresNumber of worker threads.
thresholdnumber1024Min array length before parallelizing; below it the caller thread runs fn directly.
reduce(a: R, b: R) => R—Reduce the partial results into a single value.
eagerbooleanfalsePre-spawn workers immediately instead of on first call.

parallel(data, callOptions?)

Every call accepts its own overrides, independent of the wrapper's options.

CallOptions
Option Type Default Description
coresnumber—Override the partition count for this call, within the pool cap.
signalAbortSignal—Cancel the in-flight workers.
transferbooleantrueTransfer the internally created partition buffers (see the ownership note below).

createPool<Tasks>(options)

One explicit pool over a typed worker module, shared by all registered task names. run options: signal · transfer · priority (larger first, FIFO for ties, never preempts) · timeoutMs (queue wait + execution). batch/stream add chunkSize, concurrency and per-job transfer(payload, index).

Pool contract
API Behavior
run(name, payload, options?)Always worker execution — no size threshold or silent main-thread fallback. Awaits sync/async handlers.
batch(name, jobs, options?)Ordered results. Default chunkSize: 1, concurrency: maxWorkers. Bounded outstanding chunks.
stream(name, jobs, options?)Actual completion order across chunks; input order within each chunk. Yields { index, value } with backpressure.
warmup(count?)Spawn up to the pool cap and await the module init/ready handshakes.
close()Reject new submissions, drain accepted work, await termination. Idempotent.
terminate()Reject pending/active jobs, stop workers, await shutdown. Idempotent.
statsworkers, ready, active, queued, lifecycle state, cumulative completed/failed/cancelled.

Pool options: maxWorkers · maxQueue (128) · idleTimeoutMs (30,000) · startupTimeoutMs (10,000) · onTask(timing). Default workers: max(1, min(4, cores - 1)). Cancelling a running job terminates its worker (hard cancellation — finally blocks are not guaranteed) and reschedules waiting work on surviving or replacement workers; a crash rejects only that worker's active job — tasks are never retried automatically.

Ownership: copies for multicore(), explicit moves for pools

multicore() copies TypedArray inputs into compact, independently owned partitions and transfers only those — your caller-owned buffers are never detached (disable with { transfer: false }). With task pools you list the transferables yourself (transfer: [input.buffer]) and the sender's entire backing buffer detaches, aliases included; cancellation does not restore moved inputs. SharedArrayBuffer is never transferred; shared-memory synchronization stays the caller's responsibility.

Install

🧑‍💻 Up and running in a minute

Requirements: Node.js ^18.17.1 || ^20.3.0 || >=21.0.0 or Bun 1.x on the server; any browser with Web Workers and structured clone (module workers need ES module worker support).

bun recommended

Bun 1.x works as installer, script runner and runtime — its worker_threads support runs the package as-is.

  • Add the package, then import it like any ESM dependency.
  • The repo's benches and tests run under bun run bench and bun run test.
bun add defuss-multicore

npm · pnpm · yarn

Zero dependencies and dual ESM + CJS output: import and require both resolve, with types for both module systems.

  • Subpath export defuss-multicore/worker carries expose and transfer for worker modules.
npm install defuss-multicore
pnpm add defuss-multicore · yarn add defuss-multicore

Node.js

worker_threads under the hood. Top-level await needs an ES module: a .mjs file or "type": "module" in your package.json.

  • Developed and verified on Node 24; engines allow ^18.17.1 || ^20.3.0 || >=21.0.0.
  • See examples/node in the repository for a runnable project.
import { multicore, getPoolSize } from "defuss-multicore";
 
console.log(`using ${getPoolSize()} worker_threads`);
 
const parallelSum = multicore(
  (chunk) => chunk.reduce((a, b) => a + b, 0),
  { reduce: (a, b) => a + b },
);
 
console.log(await parallelSum(Array.from({ length: 10_000_000 }, (_, i) => i)));

Browser + Vite

Web Workers under the hood. Keep the worker expression at the application call site so Vite can bundle the worker graph — the same pattern the examples/vite project uses.

  • Set worker.format: "es" when your worker module uses top-level await.
  • The repo's browser tests drive real Chromium workers via Playwright.
import { createPool } from "defuss-multicore";
import type { tasks } from "./worker.js";
 
// keep this expression at the call site so Vite bundles the worker graph
const pool = createPool<typeof tasks>({
  worker: () => new Worker(new URL("./worker.ts", import.meta.url), { type: "module" }),
});
import { defineConfig } from "vite";
 
export default defineConfig({
  worker: { format: "es" },   // allow top-level await in worker modules
});

Nine cores idle while one does all the work?

One import, one call: split the batch across every core, in the browser and Node.js alike. Loop-unrolled kernels for the math that stays on the caller thread, task pools for the modules that cannot.
